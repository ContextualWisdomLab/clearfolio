# ADR-0003: Use purpose-separated, domain-separated audit pseudonymization

Status: Proposed
Implementation maturity: `ACTIVE_PR` #270/#268

## Context and drivers

Audit evidence needs stable correlation without writing raw approver/operator identifiers or approval tokens. Reusing a policy-signing key for audit pseudonymization couples unrelated purposes and increases blast radius. Plain unsalted hashing of low-entropy identities is not an adequate pseudonymization boundary.

## Alternatives

1. Store raw identifiers in audit events.
2. Store plain SHA-256 identifiers.
3. Use a versioned domain-separated HMAC with an audit-only key and retain raw identity only at its authorized source.

## Decision

Choose alternative 3. Audit pseudonyms use **HMAC-SHA-256** with an audit-only key and an explicit, versioned domain/context prefix. Clearfolio policy requires at least **32 uniformly random bytes (256 bits of generated key material)** for a production audit-pseudonymization key; this is an application policy chosen to match the SHA-256 security target rather than a claim that NIST mandates that exact byte count. A human password, low-entropy phrase, reused signing secret, or truncated identifier is not acceptable key material.

Production key material must be generated by an approved cryptographically secure generator and held by an authenticated secret manager/KMS or equivalent credential registry that enforces access control, auditability and purpose separation. Environment variables may be bounded bootstrap transport where deployment policy permits, but raw process environment is not the accepted long-term production key authority. Audit-pseudonym, artifact-token, tenant-claim, policy-signing, model and repository-automation credentials are distinct purposes and must not share key material.

Length is necessary but not sufficient evidence of acceptable key generation. Clearfolio must not infer unpredictability from a 32-byte value alone: production configuration also requires an approved provenance classification bound to the loaded credential, such as CSPRNG-generated material registered by the credential authority or a KMS-generated/held key. Known placeholders, repeated-byte values and deterministic low-entropy fixtures are explicit negative cases, and a credential whose approved provenance cannot be established fails closed. This provenance rule avoids pretending that arbitrary key bytes can prove their own randomness.

Pseudonym records carry a key/version identifier such as `v1` plus the domain context. New writes use only the currently active version. During a bounded rotation/retention window, authorized readers may recognize explicitly configured predecessor versions to interpret retained evidence; they must not silently downgrade new writes, accept an unconfigured version, or rewrite historical pseudonyms without a privacy-reviewed migration. Once retention/rollback requirements for a predecessor expire, that key version is disabled and destroyed according to credential policy. Pseudonymized values remain personal data and remain subject to access/retention controls.

## Consequences

Cross-event correlation is possible within the intended domain, while direct identifiers are omitted from ordinary audit output. Key rotation/versioning, authenticated credential storage and purpose-specific configuration become operational requirements.

## Failure and recovery

Missing, shorter-than-policy, non-random/placeholder, provenance-unverified, improperly shared, unavailable or unrecognized-version required keys fail closed in production-configured paths. Rotation preserves version-aware interpretation without requiring raw historic identifiers to be rewritten. Recovery restores an authorized key version only from the governed credential backup/recovery mechanism; application logs or audit payloads are never a recovery source.

## Security and privacy

Do not log raw approval tokens, raw subject/tenant identifiers where pseudonymized evidence suffices, signatures, uncontrolled exception text, filenames/paths/digests in low-cardinality telemetry, or secret material. HMAC pseudonyms are not anonymization.

## Compatibility and migration

Existing raw/plain-hash evidence must not be silently relabeled. New evidence records the pseudonymization version/domain. Any migration of retained legacy evidence requires a privacy review. Key rotation is additive first: introduce and verify the new version, switch new writes, retain the prior version only for the bounded read/rollback window, then retire it.

## Tests and acceptance

- production key-strength/provenance acceptance rejects fewer than 32 bytes, known placeholder/default material, repeated-byte 32-byte values, other deterministic low-entropy fixtures, and any key lacking approved CSPRNG/KMS/credential-registry provenance; a positive fixture proves an approved provenance-bound 32-byte-or-stronger key is accepted;
- purpose-separation test rejects reuse of audit pseudonymization key material by artifact-token, tenant-claim or policy-signing authority;
- deterministic same-domain correlation and different-domain non-equality;
- version test accepts only explicitly configured active/predecessor versions and proves new writes never downgrade;
- rotation regression proves active-version switch, bounded predecessor reads and final predecessor retirement;
- credential configuration test proves production fail-closed behavior when the authenticated key authority is unavailable;
- no raw identifier/token/key logs;
- standalone/Spring fail-closed construction;
- exact-head owned production statement/branch coverage and security review.

## Rollback / supersession

Rollback may disable a new audit consumer but must not restore raw identifier logging or an already-retired weak/shared key. Supersede only with a privacy-reviewed construction having equal or stronger separation, key-management and rotation semantics.
